# SwirEngine 2.0 — Runtime scalability and resource lifecycle

- hardened `AssetStreamingManager` so cancelled and exceptional background futures are drained deterministically instead of escaping `pump()` or leaving sticky pending work;
- added explicit closed-state semantics, session teardown through `release_all()` / `shutdown(release_resident=True)`, peak resident asset tracking and separate cancellation diagnostics;
- surfaced unresolved pinned-resource pressure with `over_budget` and `budget_pressure_events` rather than silently pretending the configured residency budget is satisfied;
- reconciled externally invalidated cache entries before re-staging so stale residency metadata cannot force synchronous decode/file work onto the caller thread, while preserving prior pin intent across the asynchronous restage;
- isolated creator size-estimator exceptions as failed streaming results and invalidated newly loaded cache entries so cache state and residency accounting cannot silently diverge;
- expanded finalize hitch timing to include size estimation, residency accounting and budget eviction rather than measuring only completed-future retrieval;
- retained ordinary shutdown cache behavior for stable 1.x compatibility while keeping externally supplied preloaders externally owned;
- locked the existing bounded transient renderer resource pool into the same 2.0 production gate with reuse and zero-residency teardown verification;
- added deterministic repeated streaming/render-resource workloads plus production-sized 2D checks for a 16,384-cell tilemap and 4,096-sprite staging reuse;
- added a 4,096-object sparse 3D visibility workload that locks BVH pruning/object-test reduction without converting shared-runner timings into unsupported FPS claims;
- added focused regression coverage and a dedicated Python 3.10/3.13/3.14 CI gate;
- no version bump, tag, GitHub Release or PyPI publication; roadmap progress remains 3/10 until the exact implementation head and later closeout head pass required gates.
