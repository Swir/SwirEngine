# SwirEngine 2.0 Performance Evidence & Competitive Quality Audit

This document defines the reproducible evidence contract for SwirEngine 2.0 Milestone 8. It is deliberately narrower than a marketing benchmark: the goal is to catch material regressions and document creator/shipping workflow evidence without publishing numbers that are not technically comparable.

`Release/PyPI: frozen until SwirEngine 2.0`

## Measurement policy

**Shared CI timing is regression evidence, not a hardware performance promise.** Hosted-runner wall-clock values can move with CPU allocation, virtualization, cache state and host contention. Existing workload budgets are therefore deliberately generous release regressions, while stronger deterministic invariants cover allocation counts, bounded work, pruning, update counts, fallback counts and lifecycle cleanup.

**No cross-engine FPS ranking is published.** SwirEngine does not currently maintain the same scene, renderer backend, asset set, dependency versions, OS image and packaging/runtime harness across other Python engines. Cross-engine FPS, latency or memory charts under different workloads would be misleading. Milestone 8 records positive, sourceable workflow facts from official documentation instead and explicitly marks runtime performance as not compared.

The machine-readable contract is [`performance_evidence_2_0.json`](performance_evidence_2_0.json). Runtime evidence generated by CI includes the exact commit, Python implementation/version, OS, architecture, runner context, command, threshold source, observed harness duration and bounded command output.

## Reproducible SwirEngine workloads

| Scope | Command | Release regression contract |
|---|---|---|
| Runtime scheduling | `python tools/benchmark_frame_budget_1_7.py` | 10,000 frames, exact drain/item counts, existing 5 s budget |
| Creator authoring | `python tools/benchmark_editor_productivity_1_5.py` | 120-object prefab workflow, 200 iterations, no unapplied changes, existing 5 s budget |
| Multiplayer replication | `python tools/benchmark_multiplayer_replication_1_6.py` | 2,500 entities × 24 clients × 24 ticks, exact full/delta counts, zero fallbacks, existing 6 s budget |
| Renderer resource lifecycle | `python tools/benchmark_render_resources_1_8.py` | 512-pass graph × 100 frames, exactly two physical allocations, no leaked leases, existing 5 s budget |
| World streaming | `python tools/benchmark_world_streaming_2_1_5.py` | 10,000 registered cells × 1,200 focus updates, fixed 25-cell local window, existing 3 s budget |
| Production scalability | `python tools/verify_runtime_scalability_2_0.py` | bounded asset residency, transient-resource reuse, 16,384-tile locality, 4,096-sprite staging reuse and 4,096-object BVH pruning |

Run the complete evidence harness:

```bash
python tools/verify_performance_evidence_2_0.py --output build/performance-evidence.json
```

Validate only the evidence metadata and comparison policy:

```bash
python tools/verify_performance_evidence_2_0.py --validate-only
```

The JSON output is a CI/run artifact. It is not committed as a permanent benchmark score because the environment context changes between runners.

## Creator workflow evidence

The verified SwirEngine 2.0 path is intentionally end-to-end rather than an isolated API micro-benchmark:

```bash
swirengine new MyGame --mode 3d
swirengine workflow MyGame --prepare --profile windows
swirengine workflow MyGame --json
swirengine run MyGame --dry-run
```

Milestones 2, 6 and 7 already verify project preparation, machine-readable diagnostics, representative 2D/3D/multiplayer game workflows, deterministic export staging, wheel/sdist clean installs and host-native packaged-game execution. Milestone 8 treats those as creator-productivity and shipping evidence; it does not turn command count into a universal productivity score.

## Competitive workflow reference — checked 2026-09-18

This table is a documentation audit, not a winner/loser score. It records only positive facts that can be reproduced from the linked official documentation. Empty or different cells are not claims that another project lacks a capability.

| Project | Official installation/distribution evidence | Runtime performance comparison |
|---|---|---|
| SwirEngine | Current repository verifies pip-package artifacts, clean wheel/sdist installs and host-native game packages through the 2.0 M7 gate. | Internal regression workloads only |
| Arcade | [Installation](https://api.arcade.academy/en/development/get_started/install.html) documents `pip install arcade`; [PyInstaller tutorial](https://api.arcade.academy/en/latest/tutorials/bundling_with_pyinstaller/index.html) documents a one-file game bundle workflow. | Not compared |
| Panda3D | [Distribution docs](https://docs.panda3d.org/1.10/python/distribution/index) document `build_apps` / `bdist_apps`; [building binaries](https://docs.panda3d.org/1.10/python/distribution/building-binaries) documents self-contained builds and Windows/Linux/macOS targets. | Not compared |
| Ursina | [Installation](https://www.ursinaengine.org/installation.html) documents PyPI installation; [building](https://www.ursinaengine.org/building.html) documents `python -m ursina.build` and additional Nuitka/auto-py-to-exe routes. | Not compared |

A future cross-engine performance comparison is permitted only after the repository contains a common workload with equivalent content, rendering expectations, warmup, dependency versions, platform/runtime context and reproducible commands for every compared engine.

## Release interpretation

Passing this gate means the current candidate preserves the selected deterministic performance contracts and has honest, reproducible evidence about its own creator/shipping workflow. It does **not** mean SwirEngine is faster than another engine, does not establish a universal FPS target, and does not authorize the 2.0 release by itself.
